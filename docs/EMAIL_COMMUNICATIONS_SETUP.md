# Почтовый контур: настройка и сопровождение

Сверено с [настройками](../config/settings.py),
[сервисами очереди](../apps/communications/services.py),
[SMTP-провайдером](../apps/communications/providers/smtp.py),
[Celery-задачей](../apps/communications/tasks.py) и
[billing views](../apps/billing/views.py) 2026-11-11.
Это описание реализации; доступность корпоративного SMTP здесь не проверялась.
Проблемы production и последующие этапы ведутся в [BACKLOG.md](BACKLOG.md).

## Реализованные сценарии

- Запрос счёта у СК из очередного взноса.
- Передача счёта в Альянс со вложениями.
- Письмо пролонгации с автоматически созданным Excel или заменяющими его файлами.
- История отправок и попыток, ручной повтор failed-письма.

Инструкция сотруднику: [USER_GUIDE_SCHEDULED_PAYMENTS.md](USER_GUIDE_SCHEDULED_PAYMENTS.md).
Приём входящих счетов по IMAP и автоматическое сопоставление не реализованы.
Самостоятельного автоматического заполнения папки «Отправленные» нет.

## Настройки

Контур использует **свои `COMMUNICATIONS_*`**, а не `EMAIL_HOST_*` Django.
Console backend Django не превращает эти письма в локальную печать.
SMTP-провайдер универсальный: название Яндекс.Почты в прежнем заголовке
не означало обязательного провайдера.

Все имена, назначения и defaults — в
[справочнике окружения](ENVIRONMENT_VARIABLES.md#параметры-которые-читает-python).
Здесь важны связи между настройками:

- `COMMUNICATIONS_EMAIL_ENABLED` включает фактическую отправку,
  `COMMUNICATIONS_RESTRICT_TO_SUPERUSER` ограничивает доступ к кнопкам,
  `BILLING_AUTO_UPDATE_TASK_ON_EMAIL_SENT` включает продвижение статуса задачи.
- SSL и STARTTLS взаимоисключаются; параметры `COMMUNICATIONS_SMTP_*`
  должны соответствовать выданным настройкам почтового сервиса.
- Основной MailAccount выбирается по `COMMUNICATIONS_DEFAULT_ACCOUNT`.
  Пустой FROM_EMAIL может подставиться из username, домен Message-ID —
  из адреса отправителя. BCC добавляется к сохраняемым получателям письма.
- Размер вложения и SMTP timeout задаются отдельно; ограничение числа файлов
  находится в billing-формах, а не в этих env-переменных.

Конкретные SMTP-host/port/TLS задаёт администратор почтового сервиса. Секреты
хранятся в защищённом `.env.prod`. После изменения окружения требуется
пересоздание app-контейнеров по [процедуре ротации](SECRETS_ROTATION.md),
обычный restart не обновляет container env.

`MailAccount` хранит метаданные ящика, не пароль. Сервис получает или создаёт
основной аккаунт по настройкам; не меняйте production-записи «для теста».

## Жизненный цикл письма

`OutboundEmail` связан с объектом задачи через content type/object ID.
Отдельные записи содержат получателей, вложения и попытки. При создании
фиксируются текст/HTML, отправитель, технический код, Message-ID и metadata.

Письмо переводится в `queued` в транзакции, Celery-задача ставится через
`transaction.on_commit`. Worker переводит его в `sending`, выполняет SMTP,
записывает `sent` либо `failed` и результат попытки. Если сам broker недоступен,
письмо также переводится в failed. Подтверждение очереди не равно отправке,
а SMTP success не является подтверждением чтения или конечной доставки.

У задачи `max_retries=0`: автоматического SMTP-retry нет. UI повторяет только
failed-письма. Есть проверка недавних дублей для того же объекта/вида; это
защита от повторного нажатия, а не гарантия exactly-once доставки SMTP.

После `sent` billing handler продвигает статус очередного взноса только вперёд,
если включён `BILLING_AUTO_UPDATE_TASK_ON_EMAIL_SENT`. При ошибке уведомление
передаётся общему контуру Telegram/VK.

## Диагностика

1. Проверьте статус конкретного OutboundEmail и историю попыток в admin.
2. Если `queued` не движется, проверьте worker, Redis и broker URL; не создавайте
   новые одинаковые письма вместо выяснения причины.
3. Если `failed`, проверьте текст ошибки, host/port и режим SSL/STARTTLS.
4. С сервера можно проверить сетевую доступность и SMTP greeting без логина.
   Не выводите пароль, `.env` или полное окружение контейнера.
5. После восстановления SMTP выберите одно актуальное письмо и выполните
   согласованную проверку отправки; не переотправляйте весь исторический failed
   список автоматически.

Сетевая ошибка не доказывает конкретную причину на роутере/почтовом сервере.
