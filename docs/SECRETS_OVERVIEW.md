# Управление секретами Onlinepolis

Действующие значения находятся только в защищённом `.env.prod` на production.
Они не проходят через репозиторий или артефакт сборки. Статус перехода на
ограниченный доступ B-08 ведётся в [BACKLOG.md](BACKLOG.md).

## Граница доступа CI

После включения B-08 GitHub использует отдельный ключ и пользователя
`onlinepolis-deploy`, UID/GID 20001. У пользователя нет доступа к Docker socket,
группам docker/admin и произвольным командам sudo. SSH принудительно запускает
root-owned gate; shell, SFTP/SCP, rsync, PTY и forwarding через этот вход запрещены.

Разрешены только команды протокола `status`, `upload`, `activate`, `health`,
`rollback` с проверенными аргументами. Gate вызывает единственный root-owned
controller. Он проверяет архив, создаёт безопасный однообразный Docker archive
без посторонних тегов и применяет фиксированную серверную конфигурацию.

Пользователь с этим ключом **может заменить приложение**. Новый код приложения
имеет доступ к его БД, media и прикладным credentials; такой доступ является
частью права деплоя. Ограниченный SSH не скрывает секреты от нового кода приложения
и не удостоверяет независимую авторизацию по переданному SHA. Назначение границы —
убрать произвольный административный доступ к хосту.

Приложения запускаются с числовым UID/GID 10001, пустым root-entrypoint,
`cap_drop: ALL` и `no-new-privileges`. CI не задаёт mounts, user, capabilities,
команды контейнеров, nginx-конфигурацию или выполняемые root-скрипты.

## GitHub Actions Secrets

| Имя | Назначение |
|---|---|
| `DEPLOY_SSH_PRIVATE_KEY` | Новый отдельный ограниченный SSH-ключ CI |
| `DEPLOY_SSH_KNOWN_HOSTS` | Проверенная публичная host key для строгой проверки сервера |
| `DROPLET_HOST` | Адрес сервера |
| `SSH_PORT` | SSH-порт; при отсутствии используется 22 |

Имя пользователя зафиксировано в workflow: `onlinepolis-deploy`.
Прикладные пароли и `SECRET_KEY` в GitHub не добавляются.
Старые `SSH_PRIVATE_KEY`/`DROPLET_USER` и старый root deploy key удаляются только
после успешного перехода на новый workflow и отдельной проверки административного
доступа. Подробнее: [настройка доступа CI](GITHUB_SECRETS_SETUP.md).

## Защищённые файлы production

| Путь | Владелец и назначение |
|---|---|
| `/root/insurance_broker/.env.prod` | root, 0600; единая конфигурация приложения и PostgreSQL |
| `/etc/onlinepolis-deploy/compose.yml` | root; проверенная базовая Compose-конфигурация |
| `/etc/onlinepolis-deploy/security.override.yml` | root; обязательные ограничения приложений |
| `/usr/local/sbin/onlinepolis-deploy-controller` | root; фиксированные операции деплоя |
| `/usr/local/libexec/onlinepolis-deploy-gate` | root; проверка SSH-команды перед sudo |
| `/etc/ssh/authorized_keys/onlinepolis-deploy` | root; разрешённый ограниченный публичный ключ |
| `/root/insurance_broker/nginx/` | root; серверная конфигурация nginx |
| `/root/insurance_broker/certbot/` | root; сертификаты и приватные TLS-ключи |

Приватный ключ сертификата — секрет. Публичный SSH host key не является паролем,
но его подлинность проверяется по уже доверенному административному каналу.
`ssh-keyscan` сам по себе такую проверку не выполняет.

CI больше не синхронизирует checkout на сервер. Изменения host scripts, Compose,
nginx и controller устанавливает администратор из отдельно проверенного исходного
кода. Preflight CI сверяет hashes защищённых конфигураций с checkout и останавливает
выкладку при расхождении; произвольная новая конфигурация не применяется автоматически.

## PostgreSQL и ротация

`POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` находятся в `.env.prod`.
Compose передаёт их Django как `DB_NAME`, `DB_USER`, `DB_PASSWORD`.
Если legacy `DB_*` ещё присутствуют в файле, они должны совпадать с `POSTGRES_*`
либо быть удалены. Изменение `POSTGRES_PASSWORD` не меняет пароль существующей роли.

Отдельный `.env.prod.db` не используется современной схемой; удалять его следует
после проверки старых операционных скриптов и отсутствия активных ссылок.
Не копировать его содержимое в CI или терминальный вывод.

Точная последовательность смены Django/DB/provider/SSH-секретов находится в
[SECRETS_ROTATION.md](SECRETS_ROTATION.md). Для перечитывания env нужен recreate,
а не `restart`. Процедура предусматривает проверку и восстановление согласованной
пары значения в провайдере/БД и в приложении.

`SECRET_KEY_FALLBACKS_JSON` содержит JSON-массив старых Django-ключей для конечного
периода плановой ротации; default `[]`. При компрометации старый ключ не сохраняют
в fallback. Обе переменные защищаются одинаково. Добавление поддержки fallback
само по себе не меняет ключи и не завершает пользовательские сессии.

## Локальная разработка

Локальный `.env` содержит только dev credentials. Файлы `.env.prod`, приватные
SSH-ключи, дампы БД и сертификаты не добавляются в Git и не выводятся при проверках.
Тесты выполняются в изолированной копии без production env/данных и без внешней
отправки сообщений. Проверки credentials показывают только наличие/совпадение
и результат соединения, без самих значений.
