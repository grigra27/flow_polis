# Архитектура и модель данных

Сверено с кодом 2026-11-11. Здесь объединены прежние описание бизнес-системы,
карта каталогов и описание БД. Полный состав полей и ограничения задают модели
и миграции; документ объясняет связи и правила, не дублируя schema вручную.

## Приложения

| Приложение | Ответственность |
|---|---|
| [accounts](../apps/accounts) | Вход, защита от перебора, middleware и проверки прав |
| [core](../apps/core) | Общие модели/сервисы, главная, media, health, уведомления и дайджест |
| [clients](../apps/clients/models.py) | Клиенты, альтернативные названия, ИНН и заметки |
| [insurers](../apps/insurers/models.py) | СК, филиалы, виды, менеджеры, метки и ставки комиссии |
| [policies](../apps/policies/models.py) | Полисы, платежи, импорт акцептов, связь с InsFlow |
| [billing](../apps/billing) | Месячные задачи очередных взносов, письма и пролонгация |
| [communications](../apps/communications) | Ящики, исходящие письма, получатели, вложения, попытки SMTP |
| [reports](../apps/reports) | Готовые Excel-отчёты, конструктор, сохранённые шаблоны |
| [analytics](../apps/analytics) | Общие фильтры, расчёт вкладок, детализация и экспорт |

`config/` содержит настройки, маршруты, WSGI/ASGI и Celery; общие шаблоны —
`templates/`, часть app-шаблонов — в приложениях. `scripts/deploy/` — код
серверного контроллера, остальные `scripts/` — host-утилиты.

## Основные сущности

| Сущность | Назначение и связи |
|---|---|
| `Client` | Лизингополучатель; отдельная запись может выступать страхователем |
| `Insurer`, `Branch`, `InsuranceType` | Страховщик, филиал, вид страхования; у вида есть `is_osago` и `needs_prolongation` |
| `LeasingManager` | Самостоятельный справочник с филиалом, ФИО и контактами |
| `CommissionRate` | Процент `kv_percent` для пары страховщик × вид страхования |
| `Policy` | Шапка договора: стороны, ДФА, объект/VIN/год, даты, франшиза, статусы и участие брокера |
| `PaymentSchedule` | Платёж полиса: год/номер, дата, страховая сумма, премия, ставка/КВ, даты оплаты и акта, `alliance_paid` |
| `PolicyInfo` | Связь полиса с `InfoTag`: `info_field=1/2`; `info3/info4` — свободный текст в Policy |
| `BillingPeriod`, `BillingTask`, `BillingTaskEvent` | Месяц, задача one-to-one с платежом и история её событий |
| `ProlongationBatch` | Месячная партия пролонгации; это не набор отдельных BillingTask |
| `MailAccount`, `OutboundEmail` | Метаданные ящика и письмо, привязанное к бизнес-объекту |
| `OutboundEmailRecipient`, `OutboundEmailAttachment`, `EmailDeliveryAttempt` | Получатели, сохранённые файлы и попытки отправки |
| `FlowPolicySource`, `FlowPolicyLink` | Исходный свод InsFlow, общий/отдельные полисы и сохранённая revision |

## Премия, страховая сумма и КВ

- `Policy.premium_total` — вычисляемое свойство: сумма `PaymentSchedule.amount`,
  отдельного хранимого поля премии в Policy нет. Для списков используется
  агрегация/аннотация, чтобы не делать запрос на каждый полис.
- Страховая сумма находится в `PaymentSchedule.insurance_sum`. Старое поле
  `Policy.property_value` не описывает текущую модель.
- `Policy.leasing_manager` — FK на `LeasingManager`, не строка.
- `PaymentSchedule.commission_rate` — FK на `CommissionRate`;
  `kv_percent` хранится в справочнике ставки, `kv_rub` — денежная сумма
  в платеже. Не следует описывать `PaymentSchedule.kv_percent` как FK.
- `CommissionRate.effective_from` задаёт включительную границу подбора по
  `Policy.start_date`; NULL — исходные условия. Уникальны компания, вид и дата,
  дополнительно допускается ровно одна исходная версия на пару. Используемая
  версия защищена от изменения процента/границы/компании/вида.
- `Policy.commission_rate` фиксирует базу новых взносов при создании. Обычный
  `save()` не подбирает её повторно. `commission_rate_origin` различает подбор
  по дате, сохранённые условия, ручной выбор и неоднозначные старые связи.
  Миграция `policies.0026` заполняет только новые поля, не пересохраняет исходные
  поля полисов и ни одного платежа. `insurers.0017` после этого добавляет версии ВСК.
- Сигнал расчёта КВ работает только для нового платежа, наследует закреплённую
  базу полиса и сохраняет явно введённые суммы. Старые ссылки, включая NULL,
  при редактировании не дополняются и не пересчитываются. Общий денежный критерий
  нестандартной КВ находится в `apps/policies/commissions.py`: ROUND_HALF_UP до
  копейки, допуск 0,01 ₽. Отсутствующие/несоответствующие ссылки не выдаются за
  подтверждённую стандартную ставку.
- `python manage.py audit_commission_rates` выводит IDs неоднозначных полисов,
  платежей с несовпадающей компанией/видом и количество платежей без ставки;
  команда ничего не меняет. Откат приложения не должен откатывать миграции со
  ставками: новые версии уже могут использоваться договорами.
- Год страхования и тарифы рассчитываются из графика. `get_rates_by_year()`
  использует дату платежа с `installment_number=1`; неполный год без первого
  платежа не считается полным годом для расчёта тарифа.
- `policy_active`, `dfa_active`, дата закрытия ДФА, участие брокера и
  фактическая оплата — разные признаки. Конкретные выборки используют
  `dfa_deactivated_payments_q` и свои условия, а не одну общую галочку.

## Очередные взносы и почта

`billing.services.sync_period` строит задачи по подходящим неоплаченным
платежам месяца, исключая первый платёж первого года. Синхронизация удаляет
задачи, переставшие соответствовать выборке, а не только добавляет новые.
В list view есть fallback-синхронизация помимо фонового задания.

Срок запроса счёта — минус две календарные недели. Дата в письме Альянсу —
`previous_business_day(due_date)` из [date_utils.py](../apps/core/date_utils.py).
Это пятидневный календарь РФ; переносы 2026–2027 годов закреплены в коде.

Письма отправляются отдельным SMTP-провайдером через Celery после commit.
Статус BillingTask продвигается после `sent`, если включён соответствующий
флаг. [Инструкция](USER_GUIDE_SCHEDULED_PAYMENTS.md) и
[почтовый контур](EMAIL_COMMUNICATIONS_SETUP.md).

## Сквозные механизмы

- Проверки доступа — middleware, mixins, Django admin permissions и отдельные
  flow/mail-гейты; [точные правила](USERS_AND_PERMISSIONS.md).
- `django-auditlog` фиксирует изменения; `daily_digest` формирует отчёт по ним.
- Логи проходят `SensitiveDataFilter`; ошибки передаются общему контуру
  Telegram/VK. [Уведомления](NOTIFICATIONS_PIPELINE.md).
- Sentry включается DSN; callback сохраняет ошибки и отбрасывает известный шум:
  [фактическое поведение](MONITORING.md#sentry).
- Media обслуживаются через проверку авторизации, кроме трёх каталогов
  изображений справочников; [Nginx и media](DNS_SSL_SETUP.md).
- Разработка и production используют разные Compose/Dockerfile;
  [разработка](DEVELOPMENT.md), [деплой](DEPLOYMENT.md).

## Аналитика

Раздел `/analytics/` (`apps/analytics`, только суперпользователь, один пункт меню «Аналитика»): одна страница с вкладками «Сводка», «Деньги», «Продажи», «Портфель», «Страховщики», «Каналы», «Клиенты», «ОСАГО», «Качество данных». Фильтры (период, филиал, СК, вид, менеджер, переключатель ОСАГО) общие и живут в GET (`filters.py`, `AnalyticsParams`). Расчёт вкладки — `sections/<вкладка>.py`, функция `build(params, query)`. Почти каждая цифра — ссылка на список «под цифрой» (`/analytics/list/<величина>/`, `drilldown.py`) с выгрузкой в Excel (`export.py`). Портфельные определения — `portfolio.py`, денежные — `money.py`. Спека и решения — [analytics-2.0-plan.md](archive/analytics-2.0-plan.md) (архив).

Старые страницы аналитики (сводка, филиалы, страховщики, клиенты, финансы, финансовая история, временные ряды, ОСАГО) удалены 2026-10-23; их адреса ведут на вкладки или на сводку, `/analytics/v2/…` — на `/analytics/…`.

## Деньги в аналитике

Единые определения — `apps/analytics/money.py` (решение владельца 2026-10-16), их используют вкладки аналитики, главная и отчёт по имуществу:

- **Заработано** — платежи с датой согласования акта с СК (`insurer_date`) в периоде, как в ежемесячном отчёте по КВ.
- **Ждёт акта** — клиент оплатил (`paid_date`), акт ещё не согласован.
- **Отменённые** платежи не ожидаются: не оплачены и полис неактивен или взнос отсечён закрытием ДФА (`dfa_deactivated_payments_q`).
- **Ожидается по графику** — неоплаченные неотменённые платежи со сроком с сегодня; **просрочено** — то же со сроком в прошлом, в итог года не входит.
- Итог года = заработано + ждёт акта + ожидается до 31.12. Рост год к году — за одинаковые периоды (1 января – сегодня).
- Прогноз по месяцам — только заключённые договоры: будущие пролонгации не входят.

## ОСАГО

ОСАГО — обычный **Policy**, у вида страхования которого `is_osago = True` (решение владельца 2026-10-15, вопросник «ОСАГО в onlinepolis»). Отдельной таблицы нет.

- Правила: ровно один платёж (год 1, платёж 1), без страховой суммы; срок не больше года (короткие допустимы); без франшизы; КВ не больше 10% премии (`OSAGO_MAX_KV_PERCENT`) — и в **CommissionRate**, и в платеже.
- Ввод: раздел админки «Полисы ОСАГО» (прокси `OsagoPolicy` над той же таблицей, права — как на обычные полисы). В разделе «Полисы» ОСАГО не видно и выбрать нельзя.
- Из акцепта: кнопка «Из акцепта (ОСАГО)» (журнал и раздел «Полисы ОСАГО») разбирает тот же файл, что и для КАСКО, в режиме ОСАГО (`parse_accept_file(..., osago=True)`, `resolve_accept_data(..., osago=True)`): вид — всегда ОСАГО, срок — всегда год от даты начала минус день (окончание лизинга не учитывается), один платёж без страховой суммы. Предупреждения: в акцепте «ОСАГО» не «да», нет даты начала, по ДФА уже есть ОСАГО. Акцепт, разобранный для одного раздела, форму другого не предзаполняет.
- Портфель в коде делится на «весь» и «без ОСАГО»: `osago_q(prefix)`, `Policy.objects.osago()` / `.without_osago()`, то же для **PaymentSchedule**. Каждый отчёт и экран явно выбирает одно из двух.
- **Без ОСАГО:** аналитика по умолчанию (переключатель «с ОСАГО» в фильтрах), снимок по страховым суммам, четверговый отчёт, CSV платежей, на главной — страховые суммы, концентрация, индекс нового бизнеса, счётчик «не подгружен»; счётчики и средняя премия в карточках клиента/СК/филиала/менеджера и их статистика.
- **С ОСАГО:** журнал полисов (с фильтром), карточка полиса, список платежей, списки полисов в карточках, пролонгация и отчёт об окончании срока, отчёты по КВ, ежемесячный КВ, 3%, конструктор отчётов (с фильтром), на главной — разрезы по премии, просрочки, радар продлений, дайджест (с пометкой «ОСАГО»).
- **По галочке:** экспорт полисов (`include_osago=1`, по умолчанию без ОСАГО).
- Отдельно: вкладка «ОСАГО» в аналитике (`/analytics/osago/`), переключатель на неё не влияет.
- Четверговый отчёт: обе части (не подгружены документы, нет данных об оплате) — без ОСАГО и без закрытых ДФА (`dfa_active=False`), просьба учёта 2026-10-16.
- Очередные взносы ОСАГО не видят сами: единственный платёж ОСАГО — первый платёж первого года, он и так исключён.
- Регрессионная страховка: `tests/test_portfolio_regression.py` — полис ОСАГО не должен менять ни одной цифры в разделах «без ОСАГО».

## Связь с InsFlow

Ссылка на полис появляется в открытых карточках свода и сделки ЗС, когда менеджер сохраняет новый договор или подтверждает связь с существующим. Сотрудник может открыть договор до начала действия, после окончания срока и после расторжения. Один договор открывается сразу, в том числе общий для нескольких объектов. Если договоров несколько, ссылка ведёт к полному списку по своду.

Групповой список `/policies/by-summary/<summary_id>/` отбирает полисы по сохранённой связи со сводом. Вариант `?in_force=1` использует правила действия договора на текущую дату. У каждого полиса есть позиция объекта и его собственный ДФА. Для просмотра достаточно войти в модуль. Из карточки полиса боковой блок «флоу // заявки» ведёт к связанному своду.

Источники: [flow_views.py](../apps/policies/flow_views.py),
[flow_permissions.py](../apps/policies/flow_permissions.py),
[flow_client.py](../apps/policies/services/flow_client.py),
[flow_import.py](../apps/policies/services/flow_import.py),
[flow_api.py](../apps/policies/flow_api.py).

Переход начинается из свода ЗС. `/flow/from-zs/` принимает одноразовый код,
убирает его из следующего URL и сохраняет продолжение в сессии. После входа
проверяются локальные права и серверный клиент обменивает код на snapshot.
Код продолжения привязан к сессии; в исходной ссылке нельзя публиковать секреты.
Nginx маскирует query и referer для начального перехода.

Перед сохранением выполняется повторная сверка revision. Можно создать новый
полис или подтвердить связь с подходящим существующим по ДФА; поддерживаются
общий полис и отдельные позиции группы. Запись связи выполняется транзакционно
с проверками занятых позиций/режима. Это не фоновая массовая синхронизация всех
данных InsFlow и не публичная выгрузка полиса.

Настройки: `FLOW_HANDOFF_ENABLED` (по умолчанию false), `FLOW_ZS_BASE_URL`
(по умолчанию `https://zs.insflow.ru`) и `FLOW_SERVICE_TOKEN`.
Клиент допускает HTTPS, а HTTP — только loopback в DEBUG; redirects выключены,
таймаут подключения/чтения — 3/6 секунд. Обратный endpoint
`GET /internal/flow/v1/summaries/<summary_id>/links/` использует Bearer-токен
и возвращает связи. Его авторизация проверяет токен отдельно от UI-флага.
Точные ограничения snapshot задаёт валидация `flow_client.py`.
