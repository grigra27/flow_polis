# Отчёт: бэкапы и ошибки на проде (`ssh polis`)

Дата проверки: 2026-09-19. Режим — только чтение: код и конфигурацию не менял, использовались чтение логов, cron'а, docker и самих архивов.

## Главное

**Сам бэкап работает. Ломаются проверка целостности и доставка.** Ошибки в логах настоящие, но они не про испорченные данные.

## Что работает

- Cron от root: БД ежедневно в 02:00, media по понедельникам в 03:00 (crontab `0 3 * * 1`, сервер в TZ MSK; комментарий «Sunday» в самом crontab — описка), cleanup в 04:00.
- **271 запуск из 271 завершён успешно** за весь период логов (с 2025-12-19). Пропусков дней нет, включая сегодня (02:00:01 → 02:03:55).
- Дампы валидны: все 8 файлов за 12–19 сентября проходят `gzip -t`, по 1.5M. Проверил содержимое дампа за 19.09 — 33 196 строк, корректные заголовок / `pg_dump 15.18` / `\unrestrict` в конце, **38 таблиц — посимвольно совпадают с живой БД** (`diff` списка `pg_tables` vs дампа — IDENTICAL).
- Media: volume `insurance_broker_media_volume` = 227 файлов / 54.3M, в архиве те же 227 → бэкап берёт живой том, а не мусор. Архивы недельной давности проходят `tar -tzf`.
- Инфраструктура: все 7 контейнеров Up, nginx/db/redis/celery healthy, диск 47%, RAM 60%, health-check каждые 30 мин — HEALTHY. В nginx за 7 дней **ноль 5xx**.

## Три проблемы

### 1. Telegram-канал мёртв полностью

`api.telegram.org:443` — curl exit 28 (timeout) с хоста, `[Errno 101] Network is unreachable` из контейнера. Ошибки идут как минимум с 2026-04-25, стабильно 4–5 случаев в сутки (1280 упоминаний в `backup-db.log`). За месяц через Telegram прошло лишь ~15 сообщений из ~150 — то есть практически ничего. Затронуто всё: `daily_digest`, health-check, celery, все уведомления о бэкапах. Похоже на сетевую блокировку, а не на ошибку конфига.

### 2. Проверка целостности не выполняется никогда — из-за бага в скрипте

Строка 279 `backup_file=$(backup_database)` перехватывает весь stdout функции, включая `log_info`-строки. В переменную вместо пути попадает многострочный текст, поэтому `verify_backup` пишет:

```
Backup file not found: [INFO] 2026-09-19 02:00:50 - Starting database backup...
```

и падает. **267 из 271** запусков — `Backup verification failed`. То есть заложенный в скрипт `gzip -t` на автомате не отрабатывал никогда; целостность подтверждена только вручную, вне cron'а. К самому дампу-файлу это не относится, но «зелёной галочки» о валидности бэкапа нет.

### 3. Единственная офсайт-копия — VK, и она дырявая

Файл уходит документом в VK (`docs.getMessagesUploadServer`). За последнюю неделю сбой 2 раза: 2026-09-10 и 2026-09-17 VK вернул `no_free_space/var/www/pi` и `not saved` (сторона VK). В эти ночи — `File delivery failed on all enabled channels`: Telegram не сработал, VK тоже, значит **дампа за эти два дня вне сервера нет вообще**. Локально хранение всего 7 дней.

Отдельно: из-за `set -e` и конструкции `verify_backup ... || { log_warn; }` скрипт всегда выходит с кодом 0. Ни cron, ни мониторинг не могут заметить ни п.2, ни п.3.

## Фоновый шум (не критично)

- `django.log`: за сентябрь 25 ERROR — все «Telegram network error», плюс 1 реальный баг: `PaymentSchedule.clean()`, `apps/policies/models.py:388` — `ValueError: Cannot use None as a query value` (policy 526, year/installment = None, 2026-09-14, один раз; валидация даты платежа пропускается).
- WARNING в основном — сканеры/боты: `Referer checking failed`, `CSRF cookie not set`, 404 в nginx. 12 раз — `Commission rate not found for policy: insurer=17, insurance_type=1` (нет ставки КВ, стоит проверить справочник).
- `logrotate` для `/root/insurance_broker/logs/` не настроен — `health-check.log` уже 6.0M и растёт; критично не сейчас, но ротацию стоит завести.
- Мелкий мусор в `scripts/`: файл с именем `ystemctl start cron` (опечатка в команде, Dec 2025) и каталог `scripts/~/insurance_broker_backups/` с дампом от 2025-12-09 — след старого пути бэкапа, 120K.

## Рекомендуемые шаги (решение за владельцем, в этой проверке ничего не менялось)

1. Проверить восстановление: поднять дамп 19.09 в отдельную scratch-БД и сверить счётчики — реальный restore на этом сервере не тестировался ни разу.
2. Починить `backup_file=$(backup_database)` (лог в stderr / `tail -n1`), чтобы `gzip -t` снова работал и код возврата стал осмысленным.
3. Решить с доставкой: либо прокси для `api.telegram.org`, либо признать VK основным каналом и добавить второй офсайт (S3-совместимое хранилище), потому что 7 дней локально + падающий VK — это тонко.
