## Коротко

С **28.08.2026** ни одно письмо из раздела «Очередные взносы» (запрос счёта в СК, передача счёта в Альянс) не ушло. Причина — не в проекте и не в сервере `polis`: на почтовом сервере `mail.on-linebroker.ru` (`109.167.205.60`, сеть ЭР-Телеком / Дом.ру, судя по всему — офисный сервер за роутером) **из интернета закрыты порты отправки почты 587 и 465**. Вероятнее всего, на офисном роутере пропал проброс этих портов. Внутри офиса Outlook работает (ходит к серверу по локальной сети), а всё, что подключается снаружи — телефон на мобильном интернете и наш сервер `polis`, — отправить не может.

Нужно: попросить Никиту, который обслуживает почтовый сервер, восстановить проброс TCP 587 и 465 с внешнего адреса на почтовый сервер (текст письма — в конце документа).

## Как устроена отправка в проекте

- Письма отправляет модуль `apps/communications` (модель `OutboundEmail`, SMTP-провайдер `apps/communications/providers/smtp.py`), вызывается из `apps/billing` (раздел «Очередные взносы»).
- Настройки на проде (`.env.prod`, без секретов):

  | Параметр | Значение |
  |---|---|
  | `COMMUNICATIONS_EMAIL_ENABLED` | `True` |
  | `COMMUNICATIONS_SMTP_HOST` | `mail.on-linebroker.ru` |
  | `COMMUNICATIONS_SMTP_PORT` | `587` |
  | `COMMUNICATIONS_SMTP_USE_TLS` / `_USE_SSL` | `True` / `False` (STARTTLS) |
  | `COMMUNICATIONS_FROM_EMAIL` | `online@on-linebroker.ru` |
  | `COMMUNICATIONS_SMTP_USERNAME` / `_PASSWORD` | заданы |
  | `COMMUNICATIONS_SEND_TIMEOUT` | `30` секунд |

- Учётная запись в БД (`MailAccount`): `billing` → `online@on-linebroker.ru`, SMTP, активна, по умолчанию.

## Почему это не наша сторона

- **Изменений не было:** между 20.08 и 01.09 в репозитории нет ни одного коммита и ни одного деплоя.
- **Нагрузки не было:** в августе 1–15 писем в день, 27–28.08 — 2–4 письма; повода для антиспам-бана нет.
- **Сеть сервера исправна:** с `polis` порты 465 и 587 у `smtp.gmail.com`, `smtp.yandex.ru`, `smtp.mail.ru` открыты — хостинг (Timeweb) SMTP не режет. Исходящий IP сервера — `109.68.215.223`, IPv6 нет.
- **Настройки не при чём:** до проверки логина/пароля дело не доходит — TCP-соединение не устанавливается.

## Что открыто на `mail.on-linebroker.ru` из интернета

Проверка с сервера `polis` (2026-09-25):

| Порт | Назначение | Состояние |
|---|---|---|
| 25 | приём входящей почты (MX) | **открыт**, отвечает `mx.on-linebroker.ru` |
| 993 | IMAP (чтение почты) | **открыт**, `IMAP4rev1 proxy server ready` |
| 80 | — | TCP принимается, HTTP-ответа нет |
| **587** | **отправка почты клиентами (STARTTLS)** | **закрыт** — пакеты молча отбрасываются (таймаут) |
| **465** | **отправка почты клиентами (SSL)** | **закрыт** — `Connection refused` |
| 443 | HTTPS | закрыт |
| 110, 143, 995 | POP3 / IMAP без шифрования / POP3S | закрыты |

Трассировка TCP до порта 587 доходит до последнего маршрутизатора перед сервером (`109.167.205.62`) и обрывается на самом `109.167.205.60`; до порта 993 по тому же маршруту — проходит. То есть фильтрует именно конечная точка (роутер/файрвол офиса), а не провайдерская сеть по пути.

**Оговорка про проверки с ноутбука:** с рабочего Mac (через VPN, внешний IP `83.229.15.193`) «открытыми» выглядят вообще все порты, включая заведомо лишние (2525, 7071, 8443) — VPN сам принимает соединения. Поэтому эти проверки недостоверны и в выводах не используются; опираемся только на проверки с `polis`.

## Проверки, которые стоит сделать до письма (по желанию)

1. Телефон подключить к **офисному Wi-Fi** и отправить письмо. Уйдёт → точно проброс на роутере.
2. Outlook проверить **вне офиса** (из дома). Ожидается, что отправка там тоже не работает.
3. В Outlook посмотреть адрес сервера исходящей почты: если это внутренний адрес (`192.168.x.x`) или локальное имя — ещё одно подтверждение.

1. С `polis` проверить, что порт 587 отвечает приветствием `220` (без логина и без отправки письма).
2. Отправить заново 13 писем со статусом «Ошибка» (id 374–385) из интерфейса «Очередных взносов» — предварительно проверить, какие из них ещё актуальны.
3. Отдельной задачей — алерт в Telegram/VK на письма со статусом «Ошибка»: сейчас ошибки отправки не пишутся в `django.log`, а логи Celery теряются при деплое, поэтому сбой почти месяц оставался незамеченным. **Сделано и задеплоено 2026-10-13:** при переходе письма в failed — сообщение в VK + Telegram (`apps/communications/services.py`, `_notify_email_failed`); уже существующие 14 failed-писем алерт не порождают.

## Попутно замечено

- Логин/пароль ящика `online@on-linebroker.ru` не проверялись — для этого нужен открытый 587/465. Пробовать логин через порт 25 не стали: неудачные попытки могли бы засчитаться почтовым сервером как подбор пароля.
- SPF-запись домена `on-linebroker.ru` заканчивается на `+all` («отправлять от имени домена может кто угодно») — это позволяет подделывать письма от имени домена. К текущей проблеме не относится, но стоит заменить на `~all` или `-all` (можно упомянуть Никите).
